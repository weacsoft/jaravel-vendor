架构原则
安装 ≠ 启用：驱动按需注册

对齐 Laravel 的心智模型，把依赖放进 classpath 只表示「这个驱动可用」，不表示「要启用它」。凡是需要外部资源的驱动型模块（redis 缓存、redis session、database 缓存、redis/database 队列等），只有在用户显式选用时才注册与配置；否则完全静默：不创建任何 Bean、不连接任何外部服务、不影响应用启动。

典型反例：项目引入了 session-redis 依赖但 jaravel.session.driver 配的是 file。若 session-redis 仍自动装配并连接 Redis，就会导致无 Redis 环境启动失败。

驱动模块启用条件未启用时
session-redisjaravel.session.driver: redis不装配，回退 CookieSessionStore
redis-cachejaravel.cache.stores.*.driver: redis不装配，不连接 Redis
cache 的 database 驱动jaravel.cache.stores.*.driver: database不装配，无需数据源
queue-databasejaravel.queue.driver: database不装配，回退 sync

storage — database 磁盘jaravel.storage.disks.*.driver: database不装配

以上所有驱动统一通过 core 的 OnDriverInUseCondition（仅依赖 spring-context）判定，子类声明「驱动名 + 配置键」即可。每个驱动模块还提供 auto-register 覆盖开关（优先级最高，true 强制启用 / false 强制关闭）。

兜底默认驱动：用户写了模块配置块但没写具体 driver 时，由对应模块的 Registrar 填上模块默认值保证基本可用——auth→session、cache→array、storage→local、session→cookie、queue→sync；database 无兜底、没写连接直接报错；JWT 不在任何兜底列表中，只有显式 driver: jwt 才装配。兜底默认驱动的条件类调用 matchIfAbsent() 认缺省，非默认驱动（jwt / database / redis）严格按需、不认缺省。

不要用 @ConditionalOnBean(DataSource.class) 之类判断驱动是否可用。 它把模块和 Spring 的 Bean 图强绑定，时序脆弱，且无法感知 jaravel 自己的 @RegisterConnection 连接注册表。正确做法是运行时惰性解析：先查 jaravel 的注册表，再回退 Spring 容器。

注册式三层优先级：声明 → 配置 → 默认。驱动型模块并非只有一种注册手段：① 声明（support）——模块/开发者用 @RegisterGuard / @RegisterProvider / @RegisterDisk 等注解自我声明「我实现了哪个 driver」，开发者不动核心即可在业务工程注册额外扩展（如用 JWT 替换 session 守卫）；② 配置（yaml）——用户在 jaravel.<模块>.guards/disks/stores 里写 driver 名选用；③ 默认（兜底）——见上。另需注意：provider 不是一种 driver——同一 provider 类可对应多个对象（不同 model 类），此时把「model 类 + provider」合并看作具名别名，通过 @RegisterProvider("users") 声明、按别名解析。

功能型模块（wire、schedule、captcha、plugin-* 等）不需要外部资源，默认启用，通过 jaravel.<模块>.enabled: false 关闭，不适用本原则。但其中带「驱动」的模块（storage 的磁盘、auth 的 guard、cache 的 store 等）即便模块本身启用，其内部具体驱动仍按「用上了才装配」：本地磁盘 / session 守卫作为兜底默认始终存在，redis / database / jwt 等外部资源驱动则严格按需。

数据源解析顺序：先框架，后 Spring

任何需要数据源的模块（cache 的 database 驱动、migration、storage 的 database 磁盘）都不直接依赖 Spring 的 DataSource Bean，而是按以下顺序在运行时解析：① jaravel ConnectionManager 注册表（@RegisterConnection 声明的连接）；② Spring 容器（同名 Bean → 主 DataSource Bean）。这与 Model 的连接解析语义完全一致。

反过来，为了让 Spring 生态（DataSourceTransactionManager、JdbcTemplate 及第三方 @ConditionalOnBean(DataSource.class)）也能工作，database 模块会把默认连接以 JaravelDataSource（惰性委托）的形式注册为 @Primary 的 Spring Bean：

  • 标记 @RegisterConnection(defaultConnection = true) 的连接即默认连接；
  • 若一个都没标记，则第一个注册的连接自动成为默认连接；
  • 该 Bean 惰性求值，因此不会与 @RegisterConnection 的扫描时机冲突；
  • 若业务工程自己定义了 DataSource Bean，框架自动让位（@ConditionalOnMissingBean）。

因此业务工程不再需要手写 @Bean DataSource，只写 @RegisterConnection 即可。

热加载与远程执行独立可用

热加载插件系统和远程执行系统都可以独立于 jaravel 框架使用，仅依赖 SpringBoot：

  • 热加载：引入 plugin-jar-core 即可在任何 SpringBoot 项目中使用 JAR 插件热加载
  • 远程执行：引入 plugin-jar-remote-server + plugin-jar-remote-client 即可实现分布式方法调用（无需 plugin-jar-core，通过 BeanResolver 从 Spring 容器获取 Bean）
  • 两者结合：远程执行 + 热加载 = 分布式插件热更新，子节点自动同步新版本插件
  • SpringBoot 双版本兼容：热加载插件模块（plugin-jar-core, plugin-java-core）编译期不依赖 javax/jakarta Servlet API，通过 NativeWebRequest 抽象层 + 反射在运行时适配宿主版本，同一构件可运行在 SB 2.7（Spring 5.3, javax.servlet）和 SB 3.x（Spring 6, jakarta.servlet）环境中
配置重构（v0.1.2）

v0.1.2 对 jaravel 的配置体系进行了重构，采用类似 Laravel config/app.php 的中央配置模式，通过 @Import 注解显式控制各功能模块的启用，而非依赖约定自动激活。

设计理念：大部分功能应显式启用/激活，而非约定自动生效。这使开发者对框架行为有完全的可见性和控制力，避免「引入依赖即自动激活所有功能」带来的意外行为。

3. 树形拓扑

树形拓扑（中继转发）

当单个子节点无法独立完成插件执行（本地未加载目标插件）时，可通过树形中继转发将请求逐级下发给子节点的子节点，实现多层级联执行。此能力由 relay-enabled 开关控制，默认关闭，保持向后兼容。

架构图

                        ┌──────────────────┐
                        │  Coordinator     │  (plugin-jar-remote-client 主节点)
                        │  协调器/根节点     │
                        └────────┬─────────┘
                                 │ registerChildNode
                ┌────────────────┼────────────────┐
                ▼                ▼                 ▼
        ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
        │  Node-A      │ │  Node-B      │ │  Node-C      │  (中继层)
        │ relay=true   │ │ relay=true   │ │ relay=false  │
        └──────┬───────┘ └──────────────┘ └──────────────┘
               │ registerChildNode
        ┌──────┴───────┐
        ▼              ▼
  ┌────────────┐ ┌────────────┐
  │  Node-A1   │ │  Node-A2   │  (叶子层，仅本地执行)
  └────────────┘ └────────────┘

请求流向：Coordinator → Node-A（本地无插件，中继转发）→ Node-A1（本地执行成功，返回结果）。

三层架构

本模块采用三层分离设计，核心逻辑不依赖 SpringBoot，可独立用于非 Spring 环境：

层级类说明
**核心层（无 SpringBoot）**RemoteProtocol、ProtocolCodec、ExecuteRequest、ExecuteResponse、RemoteTransport协议常量、帧编解码、请求/响应模型、传输抽象。纯 POJO，无 Spring 依赖
**SPI 层**BeanResolver、SpringBeanResolverBean 解析器接口及其 Spring 默认实现。解耦远程执行与具体 Bean 来源（热加载插件或 Spring 容器），使本模块可独立于 plugin-jar-core 使用
**服务核心层**RemotePluginServer、HttpRpcHandlerTCP 服务端实现与 HTTP RPC 处理工具，含中继转发逻辑。通过 BeanResolver 接口获取 Bean（热加载模式由 HotPluginManager 适配，无热加载模式由 SpringBeanResolver 实现），不直接依赖 Spring 容器或 plugin-jar-core
**适配层**RemoteServerProperties、RemoteServerAutoConfigurationSpringBoot 配置属性与自动装配。enabled=true 时自动创建并启动 RemotePluginServer，并通过 @ConditionalOnClass/@ConditionalOnMissingClass 自动选择 BeanResolver 实现

中继转发流程
  • 本地执行：收到执行请求后，RemotePluginServer.executeWithRelay 优先尝试本地执行（通过 tryLocalExecute 获取插件 Bean 反射调用）。
  • 转发子节点：本地无此插件（tryLocalExecute 返回 null）且 relayEnabled=true 时，调用 relayToChildren 轮询选择在线子节点，通过 forwardToChild 经 TCP 转发。
  • 防环检测：转发前调用 ExecuteRequest.markVisited 标记本节点已访问并递增跳数，子节点收到请求后检查 visitedNodes 是否包含自身。

executeWithRelay(request)
  ├── 防环检查：visitedNodes 包含本节点？→ 拒绝
  ├── 跳数检查：currentHop > maxHops？→ 拒绝
  ├── tryLocalExecute(request) → 本地有插件？→ 返回结果
  └── relayEnabled && 有子节点？
        ├── relayToChildren(request)
        │     ├── markVisited(nodeId)  // 标记访问，跳数+1
        │     ├── 轮询选择在线子节点
        │     └── forwardToChild(child, relayRequest)  // TCP 转发
        └── 无中继能力 → 返回 "Bean 未找到" 错误
防环机制（三重保护）

树形转发通过三重机制防止请求环路：

保护机制字段/参数作用
**visitedNodes**ExecuteRequest.visitedNodes已访问节点 ID 列表。子节点收到请求时检查自身是否在列表中，若在则拒绝执行，防止环路
**maxHops**ExecuteRequest.maxHops / RemotePluginServer.maxHops最大跳数限制（默认 5）。每转发一次 currentHop +1，超过 maxHops 即拒绝转发
**maxDepth**SubServerRegistry.maxDepth树形注册最大深度（默认 5，客户端侧）。注册子节点时若深度超过限制抛出 IllegalStateException，从拓扑构建阶段即阻断过深层级
向后兼容
  • relay-enabled 默认为 false：未配置时服务端行为与原有扁平模式完全一致，仅本地执行，不转发。
  • 树形路由元数据字段（sourceNodeId/visitedNodes/maxHops/currentHop）在扁平模式下保持默认值，不影响原有逻辑。
  • 现有 MSG_EXECUTE_REQUEST 消息类型照常处理；树形转发使用独立的 MSG_RELAY_REQUEST/MSG_RELAY_RESPONSE 消息类型，互不干扰。
树形路由

当子服务器数量较多或需要多层级联时，可启用树形路由模式。该模式下协调器按树形层级路由请求，根子服务器（直接子节点）本地执行不了时由其 RemotePluginServer 中继转发给孙节点，实现多层级联执行。

配置

jaravel:
  plugin-jar:
    remote:
      client:
        enabled: true
        transport: tcp
        # 树形路由配置
        tree-routing-enabled: true   # 启用树形路由（优先转发给根子服务器）
        max-hops: 5                  # 请求最大跳数（防环）
配置项类型默认值说明
tree-routing-enabledbooleanfalse是否启用树形路由。启用后协调器优先转发给根子服务器，并在请求中携带路由元数据防止环路
max-hopsint5请求最大跳数限制。超过此跳数的请求将被拒绝
层级路由策略

启用树形路由后，RequestCoordinator 采用以下层级路由策略：


协调器（Coordinator）
  │  1. 优先本地执行
  │  2. treeRoutingEnabled=true → 优先选择根子服务器（isRoot()）
  │     并按中继能力排序（relayEnabled=true 优先）
  │  3. 携带路由元数据：sourceNodeId / visitedNodes / maxHops
  ▼
根子服务器（Node-A，relayEnabled=true）
  │  本地无插件 → RemotePluginServer.executeWithRelay 中继转发
  ▼
孙节点（Node-A1，relayEnabled=false）
  │  本地执行成功 → 返回结果
  ▼
结果沿原路返回：Node-A1 → Node-A → Coordinator
  • 根节点优先：树形模式下协调器优先将请求转发给根子服务器（parentId 为空的节点），由根子服务器决定本地执行还是中继转发。
  • 中继能力排序：候选子服务器按 relayEnabled 排序，具备中继能力的节点优先，确保请求能继续向更深层级转发。
  • 路由元数据：转发时在 ExecuteRequest 中设置 sourceNodeId（协调器节点 ID）、visitedNodes（已访问节点列表，初始包含协调器自身）、maxHops（最大跳数），防止环路。
  • 向后兼容：tree-routing-enabled 默认 false，未启用时协调器行为与扁平轮询模式完全一致，直接轮询所有在线子服务器。
树形注册

通过 RemoteExecutionDispatcher.registerChild 或 SubServerRegistry.registerChild 注册树形层级关系，自动维护父子关系与节点深度：

// 查看树形结构

4. 与热加载结合

远程执行 + 热加载结合

远程执行和热加载是两个独立的功能，但可以组合使用，实现分布式插件热更新：

组合架构

  开发者编译新插件 JAR
        │
        ▼
  主节点（协调器）
    ├── 热加载新 JAR 插件（plugin-jar-core）
    ├── 注册到子服务器（remote-client）
    │
    ├── 子节点 A ──→ 热加载同一 JAR（plugin-jar-core + remote-server）
    │   └── 孙节点 A1 ──→ 通过中继转发获取最新版本
    │
    └── 子节点 B ──→ 热加载同一 JAR
使用方式
  • 主节点安装 plugin-jar-core + plugin-jar-remote-client
  • 子节点安装 plugin-jar-core + plugin-jar-remote-server
  • 主节点热加载新 JAR 后，子节点通过远程执行获取新插件的方法
  • 如果子节点也安装了热加载，可自动同步 JAR 文件并热加载
关键设计
  • 热加载（plugin-jar-core）和远程执行（remote-server/client）是两个独立分类
  • 两者都可独立使用：只用热加载（单机插件），或只用远程执行（远程调用已有 Bean）
  • 两者都仅依赖 SpringBoot，不强依赖 jaravel 的路由/模板/ORM 等功能
  • 组合使用时，热加载负责本地插件生命周期，远程执行负责跨节点方法调用

Module: 跨模块专题 | Version: 0.1.2

当应用从单机部署扩展到服务器集群（多实例）部署时，必须解决会话（Session）共享与缓存（Cache）共享问题。Jaravel 通过 session-redis 与 redis-cache 两个模块，配合 redis-config 基础设施模块，提供开箱即用的集群共享方案。所有节点连接同一 Redis 集群，会话与缓存数据集中存储，任意节点的写入对其他节点立即可见。

Session 共享（session-redis 模块）

session-redis 模块将对齐 Laravel SessionManager 的会话存储后端切换为 Redis，实现多节点会话共享。核心机制：

  • 存储结构 —— Redis Hash：每个会话以 Redis Hash 存储，Key 为 session:{sessionId}，Hash 字段为会话数据项。相比 String 存储整段序列化数据，Hash 结构支持单字段读写，减少序列化开销。
  • 会话标识 —— Cookie Session ID：会话 ID 通过 Cookie 下发到客户端（默认 Cookie 名 JARAVEL_SESSION）。客户端每次请求携带该 Cookie，服务端据此从 Redis 加载会话。无论请求落到哪个节点，只要携带同一 Session ID，即可恢复同一会话。
  • 过期策略 —— 滑动过期（sliding expiration）：会话不是固定过期时间，而是每次访问时刷新 TTL（默认 120 分钟）。只要用户持续活跃，会话不会过期；超过 TTL 无活动则自动失效。实现上每次 session.save() 时执行 EXPIRE 重置过期时间。
特性说明
存储后端Redis Hash（session:{id}）
会话标识Cookie Session ID（JARAVEL_SESSION）
过期策略滑动过期（每次访问刷新 TTL）
序列化JSON（会话数据项逐字段存储于 Hash）
多节点一致性所有节点连接同一 Redis，会话数据全局共享
故障转移节点宕机不影响会话，请求转发到其他节点仍可恢复会话

// 会话读写：任意节点操作，全局可见
Session::put("user_id", user.getId());
Session::put("role", "admin");

// 另一节点读取同一会话（通过 Cookie Session ID 定位）
Integer userId = Session::get("user_id");

Cache 共享（redis-cache 模块）

redis-cache 模块将对齐 Laravel CacheManager 的缓存存储后端切换为 Redis，实现多节点缓存共享。核心机制：

  • 共享 Redis：所有节点连接同一 Redis 实例/集群，缓存 Key 统一前缀（如 cache:），任意节点的写入对所有节点立即可见。
  • 即时可见性：不同于本地内存缓存（各节点独立、写入仅本节点可见），Redis 缓存写入后，其他节点读取时立即可见，无需消息广播或缓存同步。
  • TTL 过期：支持 put(key, value, seconds) 设定 TTL，Redis 自动过期清理，无需应用层轮询。
对比项本地缓存（array store）Redis 缓存（redis-cache）
可见范围仅当前节点所有节点即时可见
一致性各节点独立，可能不一致全局一致（单一数据源）
容量受 JVM 内存限制受 Redis 内存限制（可独立扩容）
性能最快（内存直读）快（网络往返，毫秒级）
适用场景单机部署集群部署（推荐）

// 节点 A 写入缓存
Cache::put("user:profile:1", userProfile, 3600);

// 节点 B 立即可读（同一 Redis）
UserProfile profile = Cache::get("user:profile:1");

// 节点 C 失效缓存，全局生效
Cache::forget("user:profile:1");

redis-cache 与 session-redis 可使用同一 Redis 实例的不同数据库（database），或使用 redis-config 模块配置独立的命名连接（default / cache / session），实现物理隔离。

Redis 基础设施（redis-config 模块）

redis-config 模块对齐 Laravel RedisManager，基于 Lettuce 客户端管理多个命名连接，是 redis-cache、session-redis 等模块的基础依赖。支持三种部署模式：

模式说明适用场景
standalone（单机）连接单个 Redis 实例开发 / 测试 / 小规模生产
sentinel（哨兵）通过 Sentinel 集群监控主节点，自动故障转移需要高可用的生产环境
cluster（集群）连接 Redis Cluster，数据分片存储大规模数据 / 高吞吐场景

命名连接机制：redis-config 管理多个命名连接（如 default、cache、session），每个连接可独立配置 host、port、database、password、模式等。redis-cache 默认使用 cache 连接，session-redis 默认使用 session 连接，互不干扰。

部署注意事项

  • 负载均衡会话保持：使用 Redis 共享会话后，无需在负载均衡器配置会话粘性（sticky session）。任意节点均可处理任意请求，会话从 Redis 恢复。
  • Cookie 域名：确保 Session Cookie 的 domain 覆盖所有节点访问的域名（如 .example.com），使 Cookie 在所有子域名下生效。
  • Redis 高可用：生产环境推荐 sentinel 或 cluster 模式，避免 Redis 单点故障导致全局会话失效。redis-config 基于 Lettuce 客户端，自动支持哨兵故障转移与集群拓扑刷新。
  • 连接隔离：通过 redis-config 的命名连接机制，为 cache 与 session 配置不同 database（standalone/sentinel）或不同前缀（cluster），避免 Key 冲突。
  • 序列化兼容：会话与缓存中存储的对象需可序列化。集群中所有节点应部署相同版本的应用，确保类定义一致，避免反序列化失败。
  • 滑动过期与性能：会话滑动过期在每次 save() 时刷新 TTL，高频访问的会话不会过期。如需限制绝对过期时间，可在业务层额外记录首次登录时间并校验。
  • JWT 黑名单共享：若使用 JWT 认证并开启黑名单模式，应将黑名单 store 设为 redis，确保登出后所有节点都能识别失效 token。

架构更新说明（2026-08）：database 与 jblade 解耦

为避免过度耦合（用 database 的 ORM/分页不必依赖模板引擎），框架把视图渲染契约与 分页标准上提到 core 标准层，由 jblade 作为实现方：

  • core.view.Htmlable / core.view.HtmlString：免转义 HTML 值对象契约（原位于 jblade，已上移）。
  • core.view.View：视图渲染标准接口（render / exists / name）。BladeView 实现的是 core.view.View。
  • core.view.ViewManager：视图管理者标准接口；jblade.view.ViewManager 实现它。
  • core.pagination.Paginator：Laravel 风格分页器（实现 Iterable 与 Htmlable），不依赖任何具体模板引擎。

database 模块的 BaseModel.paginate() 返回的即是 core.pagination.Paginator，因此 database 不再硬依赖 jblade。分页 HTML 通过 Paginator.links(viewName) 渲染：视图引擎（jblade） 启动时经 ViewFacade.bind() 注入默认 View；若未引入 jblade（无默认视图），links() 安全降级为空串（即「没有分页视图时该方法等同于未执行」）。

权威文档见各模块 README：core/README.md 第 14 章、database/README.md 「分页标准层与模块解耦」、 jblade/README.md 第 4.0 节、MODULES.md 第 2.1.1 节。

jblade 组件插槽转义修复：插槽内容已是渲染好的 HTML，现统一包装为 core.view.HtmlString（Htmlable）注入组件，使 {{ $slot }} 原样输出、不再二次 HTML 转义；而用户通过 @component 显式传入的数据变量仍按 {{ }} 正常转义（防 XSS）。同时明确支持 {!! $html !!} 原样输出与 {{-- --}} 注释（均已覆盖于 jblade 文档 10/11.4 节）。

utils.Maps / ResponseBuilder.map（不可变 Map 便捷构造）：新增 com.weacsoft.jaravel.vendor.utils.Maps.of(...) 替代 Map.of，允许空键值而不抛异常——键为 null/空字符串视为「没有这条数据」跳过，值为 null/空字符串则保留以便模板判空/条件渲染；返回保持插入顺序的不可变 Map。该工具已下沉到 utils 模块，ResponseBuilder.map(...) 静态方法直接复用。见 utils 文档「Maps」小节与 http 文档 6.2。
